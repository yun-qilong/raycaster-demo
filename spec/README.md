# 总体架构

## 1. 概述

在一个光栅显示的交互程序上建立可复用框架。当前应用为 raycaster 演示，在 MCU（SPI 屏）与 PC（SDL）两个平台上共用同一套主逻辑。设计目标：更换应用或更换平台时，只更换对应部件并重新组装，框架与契约保持不变。

## 2. 组成部分

| 部分 | 职责 | 边界 |
|---|---|---|
| 框架 | 定义固定的处理流程（骨架）与契约 | 不包含任何具体应用、具体平台的内容 |
| 应用 | 实现变化点：主逻辑、渲染逻辑（声音另行设计） | 不接触平台，不定义流程 |
| 平台服务 | 实现契约规定的服务：输入、显示、管道、时基 | 不包含应用逻辑 |
| 组装 | 构造部件并建立连接 | 不包含业务逻辑与平台细节 |

组装是唯一同时了解应用与平台的部分。

## 3. 组件交互

数据流按层组织，方向只向下：

```
读取输入 ──▶ 主逻辑 ──发布状态 / 事件──▶ 管道 ──▶ 渲染 / 声音 ──▶ 平台服务输出
```

- 状态管道为信箱语义：覆盖旧值、只保留最新状态。渲染只呈现最新状态，跳过中间版本没有影响。
- 事件管道为队列语义：逐条处理、不丢失（声音功能使用）。
- 帧接口由宿主按各自的节奏调用；各节奏互相独立。
- 层间调用只向下，下层不回调上层；一切交互都发生在骨架定义的流程内。

## 4. 契约

契约是应用与平台之间的共同约定，内容包括输入采样的形式、管道中的数据词汇、画面缓冲的交接语义。

- 接口适配是契约的固有组成部分：平台把原生事件映射为约定形式，应用把约定形式映射为意图。这是设计内的耦合点。
- 契约可以随应用与平台的配对修订。
- 不定义脱离具体应用的通用输入抽象。

## 5. 框架的内容约束

- 框架不包含任何单方（仅应用或仅平台使用）的定义；允许包含双方共同约定的词汇。
- 复用目标：更换应用或更换平台时，框架保持不变。

## 6. 适用前提

1. 状态到画面是单向的；
2. 音频为语音式：事件触发，声音连续播放至结束；
3. 输出目标是光栅显示；
4. 逻辑以固定节拍推进，状态以快照形式发布。

封闭性判定：问题若能在应用内部与两条管道内解决，则为封闭问题，不需要修改架构；需要为骨架增加流程或增加通道时，视为超出适用范围。

声音功能不在当前设计范围内，另行设计；上述前提已为其预留。

## 7. 约束

无动态堆内存；定点运算（不使用浮点）；容器容量固定（无动态增长）；不使用异常与 RTTI；MCU 端静态分配；框架与应用不调用具体平台的接口（平台相关调用只存在于平台服务实现中）；语言标准 C++17。
